## Подтверждённая проблема

Coding agent может менять Android XML и код View, но обычная обратная связь
для UI рассчитана на человека: Android Studio Preview, эмулятор, физическое
устройство или ручной запуск screenshot-тестов. RFC формулирует цель как
машиночитаемый цикл для агента без запуска эмулятора:

```text
изменить XML/View → render → посмотреть PNG → проверить дерево и координаты → исправить
```

Одного изображения недостаточно, когда нужно доказать отступ, пересечение или
выход элемента за экран. Поэтому RFC и реализация делают View tree вторым
каналом обратной связи, а `inspect_view` позволяет получить точные bounds
конкретного `android:id`.

Источники: RFC, разделы 1–3, 16–17 и 28; `README.md`, раздел *Geometry feedback loop*.

## Исходные ограничения и решения

- Целевые проекты — Android XML/View, а не Compose. В область поддержки входят
  обычные Views, ConstraintLayout и Material Components «где это практично».
- Рендеринг опирается на Robolectric. Это не замена устройству или эмулятору и
  не обещает pixel-perfect совпадения с железом.
- CameraX Preview, WebView, SurfaceView, TextureView, OpenGL, видео, анимации
  и сложные жесты прямо исключены из MVP. Для CameraX RFC предлагает
  placeholder: ценность инструмента — проверка overlay-интерфейса, а не
  эмуляция камеры.
- Агент передаёт fixture явно. Renderer не пытается извлекать или выдумывать
  бизнес-данные из `tools:*` XML-атрибутов.
- Инструмент локальный и предполагает доверие к Android-репозиторию, потому что
  Robolectric и Gradle исполняют код проекта. Вход не позволяет передать
  произвольную Gradle-команду: используются задачи из конфигурации.

Источники: RFC, разделы 3, 14–15 и 23; `README.md`; `RendererService.kt`,
`BuildCoordinator.kt`, `McpServer.kt`.

## Что реализовано сейчас

Репозиторий содержит Kotlin/JVM MCP-сервер версии `0.1.0-SNAPSHOT`.
Через stdio он объявляет три инструмента:

| Инструмент | Подтверждённое поведение |
| --- | --- |
| `render_layout` | Валидирует запрос, создаёт временный Robolectric probe, инфлейтит XML, применяет fixture, выполняет measure/layout/draw, возвращает путь к PNG, JSON View tree, fingerprint/generation и timings. |
| `get_view_tree` | Возвращает дерево ранее созданной render session. |
| `inspect_view` | Находит один View по `id` или `@id/id` и возвращает сериализованный узел с bounds, текстом, состоянием, padding и margins. |

В `render_layout` поддержаны размеры в dp или точных px (с запретом смешивать
единицы для одной оси), density, orientation, theme, locale, night mode,
font scale, цвет фона и fixture. Fixture умеет задавать текст, hint,
content description, visibility, enabled/selected/checked, цвета, размер и
зачёркивание текста, а также изображение из локального файла, drawable или
заливки. Валидатор ограничивает формат этих значений и, в частности, требует
абсолютный существующий локальный image-файл размером до 20 MiB.

Source fingerprint охватывает Android resources, Kotlin/Java и важные файлы
Gradle-конфигурации; каталог `.android-ui-renderer` из него исключён. Для
внутренних сессий сохраняются View tree и metadata, а screenshot path
возвращается из временного probe.

Источники: `McpServer.kt`, `RendererService.kt`, `Model.kt`, `Fingerprint.kt`,
`SessionStore.kt`; тесты `FingerprintTest`, `RenderRequestValidatorTest`,
`RendererServiceTest`.

## Важное расхождение: RFC и текущая реализация

RFC версии 0.3 описывает желаемую архитектуру: persistent MCP orchestration
process и reloadable Robolectric worker JVM. При неизменном source fingerprint
worker должен переиспользоваться; после любой релевантной правки должен идти
разрешённый incremental Gradle build и restart worker. Это центральное решение
RFC, призванное избежать работы со stale classpath/resources.

В текущем режиме по умолчанию `worker.command` не задан. Поэтому
`WorkerManager` выбирает `SidecarWorker`, а тот **на каждом `render_layout`**:

1. создаёт временный Java Robolectric test и `init.gradle` в
   `.android-ui-renderer/sidecar/<UUID>`;
2. запускает allowlisted Gradle unit-test задачу с этим test source;
3. читает созданные PNG, View tree и timings.

То есть MCP-процесс и metadata живут в памяти между запросами, но default path
не даёт подтверждённого warm worker reuse из RFC. Поддержка внешней команды
worker предусмотрена в конфигурации и есть generic `ProcessWorker`, однако
готовая постоянная worker-программа или её конфигурация в репозитории не
поставляется. Это не дефект сам по себе: commit `89bc189` явно сменил подход
на integrated sidecar. Но в статье нельзя писать, что замеренный persistent
worker уже работает в типовом сценарии.

Также пока не реализован предлагаемый `check_layout` с правилами overlaps,
inside-screen и touch targets, нет именованных device profiles, activity/
fragment rendering, golden-image comparison и автоматического поиска
изменённых экранов.

Источники: RFC, разделы 4, 9, 20–22, 25–30; `Config.kt`, `Worker.kt`,
`BuildCoordinator.kt`; история Git, commit `89bc189`.

## Genesis-трейл: как возникла и менялась задача

Публичная переписка восстанавливает не только замысел, но и несколько
итераций направления работы агента.

1. Исходный человеческий вопрос: как отрендерить Android-экран без эмулятора
   или физического устройства. Затем цель уточнена: научить Codex во время
   реализации делать screenshot, проверять расположение элементов и исправлять
   UI самостоятельно.
2. После уточнения «хочу сделать MCP» обсуждение отделило XML/View от Compose
   и выбрало Kotlin/JVM + Robolectric. Первоначальная идея persistent JVM была
   затем скорректирована после замечания coding agent: Robolectric runtime не
   увидит новые XML/Kotlin без explicit Gradle refresh и invalidation classloader
   или restart worker.
3. По этому замечанию RFC был обновлён до модели: persistent MCP orchestration,
   `sourceFingerprint`/generation, allowlisted build и reloadable worker. Это
   именно пример, где человек/обсуждение скорректировали слишком оптимистичную
   первоначальную идею «одна навсегда прогретая JVM».
4. В ранней ревизии agent честно указал, что встроенный sidecar возвращал
   искусственный корневой `ViewNode`, поэтому `inspect_view` был практически
   бесполезен. В ответ владелец передал агенту документ с четырьмя критериями
   готовности: реальное дерево из того же View, что рисуется в PNG; пригодный
   `inspect_view`; честные timings; проверка production compatibility вместо
   расширения архитектуры ради новых функций.
5. Следующие Git-коммиты подтверждают реализацию части этого feedback:
   появились реальное View tree и geometry/timings, затем fixture images и
   production inflation configuration. Поздняя повторная ревизия в переписке
   признала geometry feedback loop реализованным, но отдельно заметила, что
   флаг `worker.restarted` у sidecar нельзя путать с реальным reuse worker JVM.

Переписка — доказательство постановок, проверок и изменения направления.
Она заканчивается планом acceptance test; его успешное проведение известно из
сообщения владельца и оставшихся локальных артефактов, а не из этой переписки.

## Роли человека и AI-агента

Переписка и код позволяют разделить роли без домыслов.

**Человек** сформулировал практическую проблему — дать Codex способ проверять
Android XML UI; уточнил формат решения до MCP; выбрал направление XML/View;
передавал агенту критерии готовности; запрашивал повторные ревизии и не принял
один PNG как достаточное доказательство UI-правки.

**ChatGPT в переписке** предложил первоначальную архитектуру/RFC, сравнивал
подходы и выполнял review результатов. Некоторые его ранние предположения
были ограничены дальнейшим разбором, в частности идея постоянного
Robolectric runtime без build/reload.

**Coding agent** сформулировал важное ограничение Robolectric classloader и
ресурсов, после чего реализовывал изменения в репозитории; его ранняя
самооценка также зафиксировала отсутствие реального View tree. Git подтверждает
последующие исправления, но не позволяет по одному только diff установить,
какой конкретный фрагмент написал человек, а какой агент.

Можно утверждать, что проект строился через последовательную связку
«постановка → агентная реализация → критическое review → уточнённая
постановка» и затем был применён coding agent на реальном layout.

Нельзя без лога сессии утверждать, какие именно MCP calls агент выполнил,
сколько раз менял XML, какие числа получил через `inspect_view` и какой
конкретно критерий он использовал для финального решения. Это не повод
сводить acceptance test к двум картинкам: визуальные артефакты показывают
результат рендера, но не доказывают роль MCP в процессе исправления.

## Acceptance test на реальном Android UI

После предыдущего исследования был проведён acceptance test в проекте
`stafftablet`. По подтверждению владельца, coding agent применил
`android-ui-renderer-mcp` при исправлении реального `item_cart_product` layout.

Сохранившиеся артефакты позволяют подтвердить ограниченный набор фактов:

- target project — реальный Android-проект `stafftablet`, а не fixture в
  репозитории renderer;
- в `.android-ui-renderer/sidecar/` есть временные `AndroidUiRendererProbe.java`,
  `render.png`, `view-tree.json`, `timings.json` и `init.gradle` для
  `item_cart_product`;
- в `.android-ui-renderer/sessions/` сохранены отдельные render sessions с
  `view-tree.json` и metadata; в них присутствуют реальные данные товарной
  карточки и mandatory-products UI;
- история target layout содержит исправление `TBLT-6558` «Поехала кнопка
  обязательных товаров на новой корзине» от 2026-09-10.

Этого достаточно, чтобы включить эксперимент в историю проекта как
проведённый реальный acceptance test. Этого недостаточно для выдумывания
пошаговой стенограммы. В будущей статье формулировка должна оставаться
точной: «агент использовал MCP при исправлении реального layout», но не
«агент за N итераций самостоятельно доказал отступ X», пока не появится
транскрипт или структурированный run log.

## Что проект умеет и чего ещё не доказано

Проект умеет предоставить локальному MCP-клиенту путь к PNG, сериализованное
дерево и точные координаты View после Robolectric inflation. Внутренние тесты
подтверждают валидацию и правила freshness/reuse для тестового внешнего worker.

Acceptance test и локальные артефакты снимают вопрос, запускался ли инструмент
на реальном Android layout. Но они не закрывают все production risks: у нас нет
сохранённой compatibility matrix для custom Views/Material theme, сравнения с
физическим устройством, итоговой latency по шагам или machine-readable журнала
сессии агента.

## Кандидаты на доказательные материалы

1. Диаграмма из RFC: `agent → MCP → fingerprint/build → Robolectric → PNG + View Tree`.
   В статье её нужно пометить как проектную архитектуру и отдельно показать,
   где default sidecar отличается от запланированного reloadable worker.
2. Короткий пример вызовов `render_layout → inspect_view` из README с вычислением
   правого отступа в пикселях.
3. Реальный PNG и соответствующий `view-tree.json` из `stafftablet`; такие
   артефакты сохранены локально в `.android-ui-renderer/`. Для публикации их
   надо сначала обезличить и выбрать безопасный пример.
4. Фрагмент JSON timings из `render_layout`, полученный на одном и том же
   Android-проекте в изменённом и неизменном состояниях. Это нужно собрать до
   заявления о скорости обратной связи.
5. История Git из девяти коммитов за 10 сентября 2026 как доказательство
   коротких итераций, но не как доказательство конкретных диалогов с агентом.

## Открытые вопросы владельцу перед outline

1. Можно ли восстановить или впредь сохранять структурированный run log:
   prompt агента, `render_layout`/`get_view_tree`/`inspect_view` calls,
   render IDs, исходные и финальные bounds, XML diff и итоговый verdict?
2. Почему после RFC о reloadable worker выбран integrated sidecar: это сознательная
   ставка на надёжность, временный MVP-компромисс или результат измерений?
3. Есть ли измерения unchanged-source и changed-source render на целевом
   Android-проекте? Без них не публиковать тезис о «быстром feedback loop».
4. Какую формулировку исходного дефекта и конкретной правки можно безопасно
   публиковать? Git фиксирует проблему mandatory-products button, но для
   редакционной истории нужно подтверждение владельца или лог сессии.
5. Какой публичный Android-проект или полностью обезличенный fixture можно
   использовать для визуальных примеров без раскрытия корпоративного кода,
   внутренних URL и данных?

## Редакционный вывод на текущих фактах

Самая честная будущая статья — не «агент полностью научился видеть Android UI»,
а история о том, как для агента спроектировали проверяемый контур обратной
связи: картинка для визуальной оценки плюс View tree для измерений. Real-world
acceptance test уже состоялся, однако подробная драматургия этого шага не
сохранилась. Поэтому до outline нельзя подменять технические следы красивой
реконструкцией: статья должна либо опираться на будущий структурированный log,
либо честно рассказывать о реальном применении без вымышленных точных чисел и
диалогов.
