# Я дал coding agent глаза для Android UI — но картинки оказалось мало

Когда coding agent меняет Android XML, он довольно уверенно работает с тем,
что можно прочитать: находит layout, понимает constraints, вносит diff. Но
дальше почти всегда возникала ещё одна ручная точка в процессе: я открывал
экран и решал, правда ли кнопка, текст или карточка оказались на своём месте.

Мне хотелось убрать именно это повторяемое переключение. Не передать агенту
ответственность за продукт и не объявить эмулятор ненужным, а сделать
результат его правки доступным в том же рабочем цикле, где он редактирует код.
Первой мыслью был screenshot: агент меняет XML, получает картинку и смотрит на
неё. На практике это оказалось только половиной решения.

## Ещё один ручной шаг

Обычная проверка Android UI устроена для человека. Можно открыть Preview,
запустить эмулятор, взять устройство или прогнать screenshot-тест. Во всех
случаях в критической точке нужен мой взгляд. Агент может честно описать
свой diff, но из этого не следует, что layout собрался как надо.

Для XML/View-экранов я хотел получить более короткий контур:

```text
изменить XML → отрендерить → проверить результат → исправить
```

Рендеринг я вынес в локальный MCP на Kotlin/JVM с Robolectric. Агент передаёт
layout и явно заданные данные для него, а в ответ получает результат рендера.
MCP здесь не главный персонаж: это способ не заставлять человека вручную
запускать тот же самый промежуточный шаг и передавать результат агенту.

Важна и граница задачи. Это инструмент для XML/View-проектов, а не замена
устройству. Он не обещает совпадения с физическим телефоном пиксель в
пиксель, не предназначен для Compose и не пытается эмулировать аппаратные
поверхности, видео или камеру.

## Я дал агенту screenshot

PNG сразу сделал результат видимым. Агент мог увидеть, что интерфейс выглядит
подозрительно: текст обрезан, блок неожиданно исчез, два элемента явно
наезжают друг на друга. Это уже лучше, чем менять XML вслепую.

Но картинка плохо отвечает на вопросы, которые обычно решают судьбу UI-правки:
каково фактическое расстояние между двумя View, вышел ли элемент за границу
экрана, где именно расположен нужный `id`. Человек может прикинуть это глазом.
Агенту нужна не только иллюстрация, но и проверяемые данные.

Ранняя ревизия прототипа это хорошо показала. Screenshot уже был, но sidecar
возвращал искусственный корневой узел. У такого «дерева» нельзя спросить о
реальной дочерней View, поэтому инструмент с названием `inspect_view` почти
ничем не помогал. Это был важный момент: наличие PNG ещё не делает UI
проверяемым.

Одновременно coding agent обратил внимание на другую слишком простую идею:
нельзя просто один раз поднять Robolectric runtime и бесконечно использовать
его после изменений XML или Kotlin. Иначе он рискует смотреть на устаревшие
ресурсы и classpath. Это замечание скорректировало архитектуру и убрало
соблазн выдать «прогретую JVM» за уже решённую задачу.

## Результат нужно не только видеть, но и измерять

Поворот был простым по формулировке и важным по последствиям: PNG и данные
должны рождаться из одного и того же уже разложенного layout.

После `inflate → fixture → measure → layout → draw` renderer сохраняет
картинку и настоящее View tree. В узле дерева есть идентификатор, тип, текст и
состояние, padding, margins и абсолютные bounds. Поэтому агент может сначала
увидеть экран, а затем обратиться к конкретной View и проверить координаты.

У этого контура три небольших действия: `render_layout` создаёт render
session, `get_view_tree` возвращает её дерево, а `inspect_view` даёт один узел
по `id`. Для истории важны не сами имена API, а возможность перейти от
«кажется, здесь слишком близко» к измеряемому факту. Например, сравнить край
кнопки с краем контейнера, не снимая размеры с PNG на глаз.

Так появился geometry feedback loop: картинка помогает заметить проблему,
дерево даёт геометрию, следующая правка снова проходит через тот же рендер.
Я не стал добавлять в статью больше устройства MCP, чем нужно для этого
свойства. Внутри есть fingerprint исходников и разрешённый Gradle pipeline,
которые не дают молча рендерить устаревшее состояние или передавать
произвольную shell-команду. Но это опора надёжности цикла, а не его сюжет.

## Кульминация: настоящий layout, а не учебный пример

После реализации инструмент применили в реальной UI-правке в рабочем
Android-проекте. Coding agent использовал MCP при исправлении layout товарной
карточки с блоком обязательных товаров.

От этого запуска остались технические следы: временные Robolectric probes,
PNG, View trees, timings и render sessions. Они подтверждают существенное:
renderer действительно запускался на настоящем layout, а не только на
демонстрационной fixture из собственного репозитория.

Но у этой кульминации есть честная граница. Полная стенограмма сессии агента
не сохранилась. Поэтому я не могу утверждать, какой именно был первый дефект,
какие вызовы MCP агент сделал по порядку, какие bounds получил, сколько раз
менял XML или за сколько итераций пришёл к решению. Две имеющиеся картинки
товарной карточки — полезные редакционные примеры, но сами по себе не
доказывают ни роль MCP, ни такую хронологию.

Это не отменяет acceptance test. Он подтверждает применимость контура к
настоящей работе. Просто реальный эксперимент не стоит превращать в красивую
реконструкцию, если журнал эксперимента не был сохранён.

## Что доказано — и чего не доказано

| Утверждение | Статус | Основание |
| --- | --- | --- |
| MCP рендерит настоящий XML/View layout через Robolectric | Доказано | Код, unit-тесты и запуск на реальном Android-проекте |
| После рендера доступно машинно читаемое View tree рядом с PNG | Доказано | Реализация, render sessions и сохранённые артефакты |
| Coding agent использовал инструмент в реальной UI-правке | Доказано | Подтверждение владельца и технические следы acceptance test |
| Результат pixel-perfect совпадает с физическим устройством | Не доказано | Robolectric не является устройством |
| Поддержаны все custom Views, темы и hardware surfaces | Не доказано | Такой compatibility matrix нет |
| Типовой путь использует тёплую persistent JVM | Не доказано | Default sidecar запускает отдельный probe для рендера |
| Агент самостоятельно закрыл задачу за известное число итераций | Не доказано | Подробный transcript и structured run log отсутствуют |

Мне особенно важна последняя строка. Инструменты для агента нельзя оценивать
по самому удачному screenshot или по уверенной формулировке в отчёте. Нужны
артефакты, из которых можно восстановить, что именно произошло.

## Роль инженера не исчезла

В этой истории я не передал агенту право «решать UI». Я сформулировал
ограниченную проблему, задал границы поддержки, не принял PNG за достаточное
доказательство и несколько раз возвращал работу к проверяемым критериям.
Агент участвовал в реализации, заметил риск устаревшего Robolectric runtime и
помог построить и применить контур.

Главный результат для меня не в том, что у coding agent появилась картинка.
Один screenshot делает интерфейс видимым. PNG вместе с View tree делает его
проверяемым. Именно так исчезает ручной просмотр из обычного цикла: не потому,
что я обещаю доверять агенту, а потому, что он получает артефакты, которые
можно измерить и перепроверить.

Следующий шаг очевиден: сохранять structured run log — запрос агента, render
IDs, вызовы инструментов, diff, измерения и итоговый verdict. Тогда следующий
acceptance test можно будет не только считать состоявшимся, но и воспроизвести
как инженерный эксперимент.
