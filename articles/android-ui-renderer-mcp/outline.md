# Outline: Я дал coding agent глаза для Android UI — но картинки оказалось мало

Статус: ждёт утверждения структуры перед написанием статьи.

## Основная мысль

Я пытался убрать ещё одну точку ручного участия из работы coding agent:
проверку Android UI после правки XML. Сначала казалось, что агенту достаточно
дать screenshot. Реализация показала обратное: видеть результат недостаточно,
его нужно уметь измерять и проверять. Поэтому к PNG появился View tree и
geometry feedback loop.

Это не история о том, что агент «заменил Android-разработчика». Это история
о том, как я сузил задачу до проверяемого цикла `change → render → inspect →
evidence → fix` и проверил инструмент на настоящем layout.

## Конфликт

Agent способен изменить XML быстро, но я всё ещё должен вручную открыть экран
и решить, действительно ли правка сработала. Обычная картинка подходит
человеку, но плохо подходит автоматической проверке. Первая версия подхода
показывала это особенно явно: PNG уже был, а View tree sidecar был
искусственным и почти бесполезным для измерений.

Инженерный вопрос статьи: что нужно добавить к screenshot renderer, чтобы
исправление UI стало доказуемым для агента — и где заканчиваются доказанные
возможности этого подхода.

## Hook первых абзацев

Я могу попросить coding agent сдвинуть кнопку в Android XML. Он может найти
layout, поменять constraint и даже аккуратно объяснить diff. Но потом работа
всё равно возвращалась ко мне: открыть экран и ответить на более важный
вопрос — кнопка действительно оказалась там, где должна быть?

Эмулятор и устройство решают эту задачу для человека, но оставляют человека
внутри каждого agent loop. Screenshot — первый шаг к автономности, но по нему
нельзя надёжно посчитать расстояние между двумя вложенными View. Поэтому я
перестал думать о задаче как о «генерации картинки» и начал строить
машиночитаемую render session.

## Структура статьи

### 1. Ещё одна ручная точка в agent workflow

**Задача раздела:** начать с моей ручной работы, а не с технологии.

- После правки XML agent мог подготовить diff, но проверка расположения
  элементов оставалась на мне.
- Android UI обычно проверяют Preview, эмулятором, устройством или ручными
  screenshot-тестами — все эти способы требуют человеческого взгляда в
  критической точке цикла.
- Моя цель была уже привычной для agent workflow: убрать повторяемое ручное
  переключение, но оставить проверяемый результат, а не заменить его доверием
  к текстовому отчёту модели.
- Scope сознательно ограничен XML/View-проектами; не нужно выдавать renderer
  за замену эмулятору или универсальный тестовый фреймворк.

**Артефакт:** компактная схема «XML → Robolectric → PNG + View tree».

### 2. Я дал агенту screenshot — и этого оказалось мало

**Задача раздела:** показать ложное первое упрощение и поворот истории.

- Первой идеей был renderer: агент меняет XML, получает PNG и смотрит на
  результат.
- Именно здесь MCP возникает как средство убрать ручной запуск и передать
  агенту результат рендера, а не как главный герой текста.
- Картинка решает вопрос «что выглядит подозрительно», но не отвечает
  доказуемо на вопрос «какой между элементами отступ» или «есть ли overlap».
- Coding agent указал на ограничение: один навсегда поднятый Robolectric
  runtime не увидит правки XML/Kotlin без Gradle refresh и invalidation
  classloader/worker.
- Ранняя ревизия обнаружила вторую проблему: screenshot был, но sidecar
  возвращал искусственный root node; `inspect_view` не мог дать полезные
  данные о дочерних элементах.
- Из этого выросли реальные критерии MVP: один View hierarchy после
  `inflate → fixture → measure → layout` должен стать источником и PNG, и
  дерева.

**Артефакт:** короткий conceptual diff «раньше: PNG + synthetic root / позже:
PNG и View tree из одного layouted root».

### 3. Поворот: результат надо не только видеть, но и измерять

**Задача раздела:** объяснить появление View Tree как следствие проблемы, а
не как перечень возможностей MCP.

- Один и тот же View hierarchy после `measure/layout` стал источником PNG и
  View tree: картинка и координаты больше не расходятся между разными
  рендерами.
- `render_layout` создаёт render session; `get_view_tree` выдаёт иерархию;
  `inspect_view` — один узел по ID. Эти названия нужны здесь ровно настолько,
  насколько помогают понять feedback loop.
- В node есть class, text, state, margins, padding и absolute layout bounds.
- Fixture задаётся агентом явно: renderer не выдумывает бизнес-данные.
- Fingerprint и allowlisted Gradle pipeline защищают от stale source и от
  произвольных shell-команд из MCP-запроса.

**Артефакт:** маленький безопасный JSON-пример `inspect_view`; можно взять
из README/RFC, без данных целевого приложения.

### 4. Кульминация: реальный Android layout

**Задача раздела:** показать, что история вышла из RFC и дошла до настоящей
работы агента.

- После review инструмент был применён coding agent при исправлении реального
  `item_cart_product` layout в Android-проекте.
- Сохранились технические следы: temporary Robolectric probes, PNG, View tree,
  timings и render sessions в `.android-ui-renderer/` target-проекта.
- Это доказывает, что renderer запускался на настоящем Android layout, а не
  только на тестовой модели.
- Не утверждать: точный исходный дефект, конкретные `render_layout` /
  `inspect_view` вызовы, значения bounds, число итераций или самостоятельность
  каждого шага агента — transcript этой сессии не сохранён.

**Артефакт:** только после отдельного scrub — один обезличенный screenshot и
соответствующий сокращённый View tree. Два предоставленных изображения пока
можно держать как редакционный reference, но не публиковать автоматически:
они не являются стенограммой acceptance test и требуют проверки на раскрытие
внутреннего продукта/данных.

### 5. Что этот результат доказывает — и чего не доказывает

**Задача раздела:** не дать истории превратиться в рекламный кейс.

Доказано:

- MCP может рендерить настоящий XML/View layout через Robolectric;
- render session оставляет машинно читаемое дерево наряду с PNG;
- инструмент был использован coding agent в реальной UI-правке.

Не доказано:

- pixel-perfect совпадение с физическим устройством;
- поддержка всех custom Views, сложных Material themes и hardware surfaces;
- warm persistent JVM в default sidecar path;
- конкретная скорость цикла или полностью автономное закрытие задачи без
  человека, потому что подробный transcript отсутствует.

**Артефакт:** таблица «доказано / не доказано» на 5–6 строк.

### 6. Роль инженера поменялась, но не исчезла

**Задача раздела:** завершить человеческим выводом, а не списком фич.

- Человек сформулировал проблему, ограничил scope, отверг преждевременную
  оптимизацию persistent worker и ввёл acceptance criteria.
- Agent помогал проектировать, критиковать предположения и реализовывать
  итерации.
- Главный результат — не «агент написал renderer», а созданный для него
  проверяемый контур, который делает UI-решения наблюдаемыми.

## Финальный вывод

Один screenshot делает UI видимым. PNG вместе с View tree делает его
проверяемым. Для работы coding agent эта разница важнее, чем ещё один
генератор кода: я убираю ручной просмотр из обычного цикла не обещанием, что
агент «сам разберётся», а артефактами, которые можно измерить и перепроверить.

Но проверяемость надо строить и фиксировать так же тщательно, как сам код.
Следующий зрелый шаг — сохранять structured run logs: prompt, render IDs,
инструментальные вызовы, XML diff, bounds и verdict. Тогда следующая статья
сможет рассказать не только о принципе, но и о воспроизводимом эксперименте.

## Редакционные ограничения

- Не называть работодателя, внутренние системы, адреса и названия закрытых
  репозиториев.
- Не публиковать реальные данные товарных карточек, если они не пройдут scrub.
- Не писать, что CameraX/WebView/SurfaceView или реальное устройство
  полноценно эмулируются Robolectric.
- Не превращать RFC и ChatGPT-обсуждение в доказательство runtime-фактов.
- Не придумывать transcript acceptance test: его в архиве нет.
