# CameraX + coding agent: факты и хронология расследования

## Зачем этот документ

Это фактическая база для небольшой статьи на vc.ru. Здесь зафиксировано
только то, что произошло в ходе расследования: исходный симптом,
гипотезы, эксперименты, неудачное направление, найденная причина и
подтверждённое исправление.

Главная тема будущей статьи шире CameraX: как выглядит реальная отладка
с coding agent, когда агент читает и меняет код, запускает `adb` и
`logcat`, анализирует результаты и обновляет MR, а разработчик управляет
расследованием и выполняет действия с физическим устройством.

------------------------------------------------------------------------

## 1. Исходная проблема

В Android-приложении используется сканер штрихкодов на CameraX.

У камеры фактически два потребителя:

``` text
Camera
├── Preview       → изображение, которое видит пользователь
└── ImageAnalysis → кадры, которые получает анализатор
```

При перевороте планшета на 180° происходило следующее:

-   preview камеры для пользователя ориентировался правильно;
-   кадры, поступающие в анализ, оказывались перевёрнутыми на 180°.

Это было важно разделить: проблема наблюдалась не как общий неправильный
поворот камеры, а именно как рассинхронизация поведения Preview и
ImageAnalysis.

------------------------------------------------------------------------

## 2. Как шла отладка

Отладка велась совместно с coding agent на реальном устройстве.

Типичный цикл выглядел так:

1.  разработчик просит агента начать чистую запись логов;
2.  агент запускает `adb logcat`;
3.  разработчик физически запускает экран или переворачивает планшет;
4.  агент снимает и анализирует логи;
5.  агент меняет диагностический код или реализацию;
6.  эксперимент повторяется.

Фрагмент реального взаимодействия:

``` text
— запускай запись я запущу экран
— Запускаю чистую запись CameraXBarcodeCamera.
— Запись начата.
— экран запущен
...
— запускай запись я переверну экран
— Начинаю новую чистую запись для переворота.
...
— перевернул
```

Таким образом, агент работал не только как генератор кода. Он участвовал
в цикле «гипотеза → instrumentation → физический эксперимент → данные →
следующая гипотеза».

------------------------------------------------------------------------

## 3. Первые наблюдения

Для исходного положения были зафиксированы:

``` text
displayRotation=1
imageRotation=0
image=1920x1080
ROI=Rect(614, 354 - 1306, 806)
```

В коде `ImageAnalysis` создавался с `targetRotation`, взятым из текущего
`previewView.display.rotation`.

То есть ориентация анализа была задана при создании use case.

------------------------------------------------------------------------

## 4. Первоначальное направление решения

При перевороте был замечен временной разрыв:

-   callback изменения display уже приходил;
-   внутри callback `displayRotation` всё ещё был старым;
-   спустя примерно 0,5 секунды фактическое значение
    `previewView.display.rotation` становилось новым.

Агент пришёл к выводу:

> однократного `post` недостаточно; нужно дождаться фактической смены
> `previewView.display.rotation` перед rebinding.

Это стало ключевой точкой расследования.

Для разработчика идея «подождать, пока значение обновится» и затем
сделать rebind была red flag: решение начинало зависеть от тайминга и
лечить наблюдаемую гонку ожиданием вместо объяснения причины.

Направление с задержками было остановлено до дальнейшего усложнения
реализации.

------------------------------------------------------------------------

## 5. Переход от «починить» к «доказать причину»

Вместо добавления `delay`, `postDelayed`, polling или повторного rebind
было решено сначала собрать диагностические данные.

В логи были добавлены:

-   `Configuration.orientation`;
-   `PreviewView.display.rotation`;
-   `Preview.targetRotation`;
-   `ImageAnalysis.targetRotation`;
-   `ImageProxy.imageInfo.rotationDegrees`;
-   размеры кадра;
-   `cropRect`;
-   ROI.

Целью стало не получить визуально работающий patch, а установить causal
chain: какое значение меняется при физическом перевороте планшета, какое
не меняется и почему ImageAnalysis продолжает выдавать прежнюю
ориентацию.

------------------------------------------------------------------------

## 6. Эксперимент до переворота

В исходном положении:

``` text
Configuration.orientation=2   // landscape
displayRotation=1
Preview.targetRotation=0      // в одном из диагностических состояний
ImageAnalysis.targetRotation=1
ImageProxy.rotationDegrees=0
image=1920x1080
cropRect=Rect(0,13–1920,1067)
```

Позднее перед финальной проверкой согласованное состояние выглядело так:

``` text
displayRotation=1
previewTargetRotation=1
analysisTargetRotation=1
imageRotation=0
```

------------------------------------------------------------------------

## 7. Эксперимент после переворота на 180°

После физического переворота планшета было зафиксировано:

``` text
Configuration.orientation=2
displayRotation=3
ImageAnalysis.targetRotation=1
ImageProxy.rotationDegrees=0
image=1920x1080
cropRect=Rect(0,13–1920,1067)
```

Это был ключевой результат.

Физическая ориентация display изменилась:

``` text
ROTATION_90 → ROTATION_270
1           → 3
```

Но `Configuration.orientation` осталась прежней:

``` text
ORIENTATION_LANDSCAPE → ORIENTATION_LANDSCAPE
2                     → 2
```

И главное:

``` text
ImageAnalysis.targetRotation=1
```

остался старым, хотя реальный display уже имел rotation `3`.

Поэтому:

``` text
ImageProxy.rotationDegrees=0
```

тоже не изменился.

------------------------------------------------------------------------

## 8. Root cause

Причина была подтверждена экспериментально:

**ImageAnalysis не получал новый `targetRotation` при физическом
перевороте планшета из `ROTATION_90` в `ROTATION_270`.**

Оба положения являются landscape, поэтому `Configuration.orientation` не
различает их.

Preview и ImageAnalysis в итоге жили с разным актуальным представлением
об ориентации:

``` text
Физический планшет      ROTATION_270
Preview/display          ROTATION_270
ImageAnalysis target     ROTATION_90   ← устаревшее значение
ImageProxy rotation      0             ← следствие
```

------------------------------------------------------------------------

## 9. Итоговое исправление

Первоначальный подход:

``` text
DisplayListener
→ post
→ дождаться обновления display.rotation
→ rebind use cases
```

был заменён на:

``` text
OrientationEventListener
→ calculatedRotation
→ Preview.targetRotation = calculatedRotation
→ ImageAnalysis.targetRotation = calculatedRotation
```

При повороте:

-   Preview не пересоздавался;
-   ImageAnalysis не пересоздавался;
-   `unbindAll()` не выполнялся;
-   `bindToLifecycle()` повторно не выполнялся;
-   задержки и polling не использовались.

Также было исправлено соответствие углов `OrientationEventListener` и
`Surface.ROTATION_*`: для диапазона 45..134° использовался
`ROTATION_270`, а не `ROTATION_90`.

------------------------------------------------------------------------

## 10. Подтверждение исправления

До переворота:

``` text
displayRotation=1
previewTargetRotation=1
analysisTargetRotation=1
imageRotation=0
```

После переворота:

``` text
orientationDegrees=70..79
calculatedRotation=3
displayRotation=3
previewTargetRotation=3
analysisTargetRotation=3
imageRotation=180
```

То есть после исправления:

1.  `OrientationEventListener` определил изменение ориентации;
2.  было рассчитано `ROTATION_270`;
3.  существующие Preview и ImageAnalysis получили новый
    `targetRotation`;
4.  CameraX пересчитал `ImageProxy.rotationDegrees` с `0` на `180`;
5.  rebind не понадобился.

Исправление было подтверждено на реальном устройстве.

MR был обновлён коммитом `013c5975c`.

------------------------------------------------------------------------

## 11. Отдельное наблюдение про pipeline анализа

В ходе разбора кода обнаружилось, что `ScanFrame` сохраняет:

``` kotlin
rotationDegrees = proxy.imageInfo.rotationDegrees
```

При этом ZXing-декодер строит `PlanarYUVLuminanceSource` из сырого
Y-buffer.

Это породило отдельный вопрос: где именно должен учитываться
`rotationDegrees` в полном pipeline `ImageProxy → ROI → ZXing`.

Однако подтверждённый root cause текущего дефекта находился раньше:
`ImageAnalysis.targetRotation` не обновлялся. Поэтому ручной
`rotate(180)` Y-buffer/Bitmap/ROI не добавлялся как компенсация.

Для статьи этот эпизод полезен как пример того, почему не стоит
одновременно «чинить» несколько возможных слоёв, пока не доказана
причина наблюдаемого дефекта.

------------------------------------------------------------------------

## 12. Что делал coding agent

В рамках расследования агент:

-   изучал CameraX-код;
-   менял диагностическое логирование;
-   запускал `adb`;
-   очищал и записывал `logcat`;
-   сопоставлял значения до и после физического переворота;
-   строил гипотезы;
-   предлагал изменения;
-   реализовал переход на `OrientationEventListener`;
-   обновлял `targetRotation` существующих use cases;
-   проверял результат по логам;
-   обновил MR.

Агент также предложил неудачное направление: ожидать фактического
обновления `display.rotation` перед rebind.

Это важно сохранить в статье: агент не был безошибочным исполнителем.

------------------------------------------------------------------------

## 13. Что делал разработчик

Разработчик:

-   формулировал наблюдаемую проблему;
-   взаимодействовал с физическим планшетом;
-   задавал моменты начала экспериментов;
-   запускал экран и физически переворачивал устройство;
-   оценивал качество предлагаемых решений;
-   распознал задержку/ожидание как архитектурный red flag;
-   остановил движение в сторону timing-based workaround;
-   потребовал сначала доказать root cause;
-   направил расследование к измеримым значениям;
-   принимал решение о том, какое исправление считать корректным.

Важная деталь: чтобы отвергнуть плохое направление, не требовалось
заранее знать окончательный API-ответ. Было достаточно инженерного
критерия: корректность решения не должна зависеть от случайной задержки
обновления display state.

------------------------------------------------------------------------

## 14. Главный материал для статьи

История показывает не «ИИ написал код вместо разработчика», а разделение
ролей в agentic-разработке.

Агент выполнял большую часть механического инженерного цикла:

``` text
найти код
→ инструментировать
→ собрать данные
→ изменить реализацию
→ снова проверить
→ обновить MR
```

Разработчик управлял самим расследованием:

``` text
поставить эксперимент
→ оценить гипотезу
→ распознать плохое направление
→ потребовать доказательства
→ выбрать критерий корректности
→ принять результат
```

Ключевая формула для будущей статьи:

> Coding agent не отменяет инженерное мышление. Он переносит
> разработчика с уровня выполнения каждого технического шага на уровень
> управления экспериментом и принятия инженерных решений.

------------------------------------------------------------------------

## 15. Факты, которые нельзя исказить в статье

-   Проблема была именно в потоке анализа; preview для пользователя
    ориентировался корректно.
-   Речь шла о перевороте планшета на 180° между `ROTATION_90` и
    `ROTATION_270`.
-   Оба состояния оставались `Configuration.ORIENTATION_LANDSCAPE`.
-   Агент первоначально двигался к ожиданию обновления
    `display.rotation` и rebind.
-   Это направление было остановлено как timing-based workaround.
-   Root cause был подтверждён логами, а не предположен.
-   Итоговое решение использует `OrientationEventListener` и
    динамическое обновление `targetRotation`.
-   При повороте use cases не пересоздаются.
-   После исправления `ImageProxy.rotationDegrees` изменился с `0` на
    `180`.
-   Исправление проверено экспериментом на реальном планшете.
-   Нельзя представлять агента как полностью автономно нашедшего
    правильное решение: направление расследования корректировал
    разработчик.
