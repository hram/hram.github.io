# Аудит проектов для цикла статей про AI-агентов

Дата: 15 сентября 2026. Независимый обзор (не копия
`ai-agent-article-candidates-2026-09-15.md`, хотя выводы местами совпадают —
источники одни и те же).

## Методика

Для каждого проекта из `PROJECTS.md` я зашёл в реальный каталог на диске и
проверил: состав корня, README/CLAUDE.md/PROJECT_BRIEF.md, наличие `prompts/`
(или `promts/`), дату последнего коммита, а где было сомнение — заглянул внутрь
промптов.

Одно уточнение к самой методике аудита: папка `prompts/` — неоднородный сигнал.
Я разделяю её на два разных по ценности типа:

- **genesis-промпты** — использовались, чтобы **построить** проект (мастер-план +
  пронумерованные этапы). Это и есть история для статьи: видно, как менялось
  задание, что агент сделал на каждом шаге.
- **runtime-промпты** — не история разработки, а **часть продукта**: промпт,
  который сама система на проде скармливает LLM (например, `review/prompt.md`
  для ревью постановок или `gitlab-panel/prompts/mr_review.txt` для AI-ревью MR).
  Их наличие ничего не говорит о том, как проект был написан.

Эта разница важна для отбора: проект с одним runtime-промптом и без genesis-следов
всё ещё может быть отличным кейсом, но статью придётся строить на коде и git-логе,
а не на «истории промптов».

Также я посмотрел на состояние git как индикатор зрелости для статьи (см.
колонку «Git»). Дата — дата последнего коммита; давность посчитана от 2026-09-15.

## Предлагаемый порядок публикации

Логика: сначала кейсы с полным genesis-трейлом и завершённым результатом,
подтверждённым git-историей; затем нишевые технические серии; затем кейсы,
которым нужно время на стабилизацию или на приведение в порядок git/документации.

1. **`impact-analysis`** — самый чистый и завершённый кейс: полный genesis-трейл,
   исследовательский отчёт до кода, измеримая инженерная польза, стабильный git.
2. **`android-ui-renderer-mcp`** — логичное продолжение Android-темы и новый
   жанр: агент строит инструмент для других агентов.
3. **`running-portal`** — образцовая пошаговая история продукта (11 этапов),
   активная разработка, понятная бытовая польза.
4. **`orienteering`** — сразу после running-portal, как «второй проект по тому
   же архитектурному шаблону»: что можно переиспользовать, а что пришлось
   переделать.
5. **`culatta`** — конкретный бизнес-результат, работа с грязными офисными
   форматами, плюс честная деталь про недообновлённую документацию — хороший
   урок для читателей, которые сами строят с агентами.
6. **`career-portal`** — ещё один полный пронумерованный genesis-трейл,
   более нишевый продукт, но методически показателен.
7. **`trunks-allocator`** → 8. **`demodulator`** → 9. **`signal-analise`** —
   DSP-трилогия по порядку готовности; `signal-analise` публиковать последним,
   когда фазы демодуляции будут завершены.
10. **`allure-testops-mcp`** — короткий прикладной пост для QA/DevOps.
11. **`gitlab-panel`** — сильный контент, но требует больше самостоятельной
    реконструкции истории (мало genesis-следов); публиковать, когда будет
    время написать её не по промптам, а по коду и функциональности.
12. **`doctor`** — только после полной анонимизации примеров и с явным
    дисклеймером; честно указать, что задокументирована лишь часть истории
    (разбор документов), а не весь портал.
13. **`meta-agent`** — синтезирующая мета-статья в конце основного цикла,
    когда уже есть на что сослаться.

Отдельно, вне основной нумерации:
- **Мини-серия про бытовую автоматизацию**: `ikus.pesc.ru` → `peterburgregiongaz`
  → `meters`. Публиковать одним блоком или тремя короткими постами подряд.
- **`myhome` и `procboard`** — по одному короткому посту для DIY/self-hosting
