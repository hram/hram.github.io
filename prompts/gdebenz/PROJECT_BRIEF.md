# gdebenz

## Роль

Личный портал, который превращает разрозненные данные о наличии бензина на
избранных АЗС в один понятный ответ на практический вопрос: ехать заправляться
сейчас или подождать.

## Одной строкой

Персональный сервис, который решает вопрос «ехать за АИ-95 или ждать» по
данным избранных АЗС: агрегирует внешний источник, хранит историю и
уведомляет только о значимых изменениях.

## Задача, которую решает

Когда бензин появляется нестабильно, отметки «топливо есть» недостаточно:
рядом с ней может быть очередь в 100+ машин, устаревшее наблюдение или чужая
ошибка. Портал собирает данные по конкретным АЗС и превращает их в решение
с причиной, а не в сырую ленту сообщений.

## Что это

- Серверное веб-приложение на FastAPI, Jinja2 и SQLite, собранное на основе
  внутреннего шаблона `template-python-fastapi-jinja`.
- Клиент внешнего API `gdebenz.ru`: агрегированная сводка по станции, свежие
  наблюдения, поиск ближайших АЗС.
- Отдельный worker-процесс, который периодически опрашивает избранные станции
  и пишет накопительную историю в общую persistent SQLite.
- Rule-based решатель на 4 вердикта: **ЕХАТЬ**, **ЖДАТЬ**, **НЕТ ВАРИАНТОВ**,
  **НЕТ СВЕЖИХ ДАННЫХ** — каждый с объяснением причины.
- История снимков, тепловая карта по дням, часовой таймлайн, журнал сборщика
  и Telegram-уведомления о значимых переходах состояния.

## Что демонстрирует

- **Продуктовое мышление:** сырые статусы АЗС превращены в одно решение с
  причиной, а не в список технических полей.
- **Работа с ненадёжным источником:** явные правила доверия агрегату
  `gdebenz.ru` против одиночной пользовательской отметки, отдельная обработка
  свежего противоречащего наблюдения (`freshConflict`) и устаревших данных.
- **Объяснимость вместо чёрного ящика:** каждая рекомендация формулируется как
  причина («95-й есть, но свежее наблюдение — очередь 20–50 машин, данные
  18 минут назад»), а не как скрытая оценка.
- **Доведено до эксплуатации за 1 день:** web и worker разделены на процессы,
  используют одну persistent SQLite, есть журнал ошибок и Docker-сборка.

## Стек и архитектура

- Python, FastAPI, Uvicorn, SQLite, слои `router → service → repository`.
- Jinja2 templates, без SPA-фреймворка.
- Отдельный async-клиент `gdebenz.ru` на httpx: таймауты, обработка ошибок,
  нормализация времени в UTC.
- Docker Compose: раздельные образы для web-процесса и worker'а, общий volume
  под SQLite.
- Тесты через pytest, статические проверки ruff и mypy.

## След AI-процесса

Перед кодом в репозитории зафиксирован разбор предметной области и найденного
API `gdebenz.ru` (эндпоинты, поля, ловушки вроде `status=yes` с очередью),
затем пошаговый план реализации по этапам: клиент API → модель данных →
сборщик истории → rule-based решатель → HTML-портал → JSON API → тесты и
Docker. Отдельным документом описан пересмотр решающего алгоритма после
первой версии. Это след перехода от постановки задачи к работающему личному
инструменту за один день.
